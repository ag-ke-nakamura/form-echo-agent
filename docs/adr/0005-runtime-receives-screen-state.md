# Runtime へ画面の状態を渡す（ADR-0003 の撤回）

- **Status**: accepted
- **Date**: 2026-09-04
- **Supersedes**: ADR-0003

`temp/design/` の4つの画面デザイン設計を**画面の正典**とし、それに合わせて出力契約・入力契約を書き換える。この結果、ADR-0003 が定めた「Runtime へ渡す入力を自然文だけに閉じる」を撤回し、**抽出系のタスクも画面の状態を構造化入力（`input`）として受け取る**。

きっかけは設計書のタブ3（参加可否回答）が `responses[].candidate_id` を返すことを求めている点。候補日程を ID で指すには Runtime が候補日程の一覧を知っている必要があり、ADR-0003 の結論と両立しない。ADR-0003 自身が最後の Consequence で「IDでしか表せない要求（特定の候補日程への言及を AI に解決させる等）が出た時点でこの ADR を見直す」と書いており、その時点が来た。

仕組みは新設しない。ADR-0004 が推薦系のために用意した `INPUT_SCHEMAS` の `null` を実スキーマに差し替えるだけで済む。撤回するのは ADR-0003 の**結論**であって、その中の「ID への解決は AI にとって余計な仕事」という洞察は生きている — **識別子はフロントエンドが発番し、AI は自分では作らない**。AI は渡された一覧の中から ID を選ぶだけになる。

## 各 taskId が受け取る `input`

| taskId | `input` |
| --- | --- |
| `ic-card.parse-reservation` | `null`（送るべき画面状態が無い。基準時刻は system prompt が持つ） |
| `meeting.parse-candidates` | 所要時間と**カレンダーの表示範囲**（#69 で追加）。既に選択済みの候補日程は送らない |
| `meeting.parse-availability` | 参加形式・所要時間・候補日程の一覧 |
| `meeting.recommend-schedule` | 参加形式・所要時間・参加者の名簿・参加可否表 |

`ic-card.parse-reservation` が `null` のまま残るのは重要で、ADR-0004 が `INPUT_SCHEMAS` に全 taskId を明示した理由（「まだ足していないのか、足さないと決めたのか」を区別する）がそのまま生きる。

`meeting.parse-candidates` が表示範囲（`calendar_start` / `calendar_end`）を受け取るのは #69 の帰結。候補日程を選ぶ非AI経路が2週間のカレンダーになり、週送りナビゲーションを持たない（#64 Out of Scope）ので、**職員が選べる日付はその範囲にしか無い。** 範囲を渡さないと AI は「来月の午後」に素直に来月を返し、返ってきた候補日程は1件もカレンダーに置けない（生成には成功したのに画面が変わらない）。範囲外かどうかを判定できるのは暦を解決する AI の側だけなので、与件として渡して範囲外なら聞き返させる。これは「画面の状態を渡す」というこの ADR の結論の素直な適用で、**画面が持つ制約は画面が渡す**ということである。

`meeting.parse-candidates` に既存の候補日程を送らないのは、設計書 6.2節の「来月の午後」→「火曜と木曜だけにして」という往復が `sessionId` の会話履歴で成立するため。カレンダーで手動選択した分を AI に教える必要があるのは設計書 6.3節（反映後の追加生成）だが、設計書はそこを「既存の選択に加算される」という画面側の挙動としてのみ規定していて、AI に既存を教えるとは書いていない。

## Considered Options

- **ADR-0003 を維持し、`candidate_id` を使わず日付キーの突き合わせを続ける**: 契約は動かないが、設計書を正典にするという前提（今回は画面の刷新）を部分的に破ることになる
- **参加可否だけ `input` を持ち、他は自然文のみ**: 「どのタスクが `input` を持つか」を覚えていないと読めない契約になり、ADR-0004 が `INPUT_SCHEMAS` を全 taskId 分明示した理由に逆行する
- **全面撤回（採用）**

## Consequences

- ADR-0003 の Consequence が予告していた「AI が入力に無い日付を返すと黙って落ちる」経路が消える。AI が選べる ID は渡した一覧の中にしか無い
- 候補日程が識別子を持つようになるので、`candidate-key.ts`（3項目を連結して突き合わせの鍵にする関数）は役目を終える
- `input` はサニタイズも Guardrail チェックも通らない（ADR-0004）。したがって `input` に自由文字列を置かないという制約が、抽出系3タスクにも広がる。参加者の名前を送らないのはこの制約の帰結（ADR-0008）
- 本番で候補日程が DB のレコードIDを持つようになったとき、この形はそのまま移植できる。ADR-0003 の下では移植のたびに突き合わせを書き直す必要があった
