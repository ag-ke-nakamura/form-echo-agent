# Guardrail がブロックしたときの画面メッセージの詳細度

- **Status**: accepted
- **Date**: 2026-09-05
- ADR-0021 が `playground.free-prompt`（プロンプト検証タブ）の1点に限ってこれを改訂した

Guardrail がブロックしたとき（`GUARDRAIL_BLOCKED`）、画面へ出す文言は**どのチェック種別
（プロンプトインジェクション・content filter・個人情報）が反応したか、どのスコアだったかを
一切含めない**。参照ドキュメント 9.3節が定める固定文言をそのまま使う。

> 入力内容に問題があります。個人情報（マイナンバー等）が含まれていないか確認してください。

**この1文を、ブロックの原因が何であっても同じように返す。** プロンプトインジェクションで
ブロックされた場合でも、この個人情報を名指しした文言をそのまま出す。

## Considered Options

- **原因ごとに文言を出し分ける（例: 「不適切な指示が含まれています」「個人情報が含まれています」）**:
  職員には親切だが、どの入力の言い回しがどのチェックに引っかかったかを外部から観測できる
  情報になる。プロンプトインジェクションを試す側にとっては、文言の違いがそのまま
  Guardrail の反応を見るオラクルになり、検知を回避する言い回しを効率的に探索されてしまう
  （参照ドキュメント 10.4節）
- **findings の詳細（カテゴリ・スコア）を画面にそのまま返す**: デバッグには最も便利だが、
  攻撃側に対しても同じ情報を渡すことになる。開発中の実測はログ（`invoke-task.ts` の
  `log.warn`）で確認できるので、画面に出す必要は無い
- **固定の1文にする（採用）**

## Consequences

- `GuardrailFinding.detail`（反応したカテゴリ・スコア・正規表現名）は**ログにしか出さない**。
  `handler.ts` は `GuardrailBlockedError` を捕まえた時点で `verdict` を握りつぶし、
  固定文言だけを返す
- 個人情報が原因でないブロック（例: 露骨なプロンプトインジェクション）でも「個人情報が
  含まれていないか確認してください」という、原因とはずれた案内になる。職員には不親切に
  見えうるが、10.4節の方針（回避方法を教えない）を優先する。実際に混乱が多いようなら、
  「原因を言わずに、かつ回避のヒントにならない」表現をこの ADR の範囲内で見直す
- `contracts/errors.ts` の `AI_ERROR_CODES` にはコードだけを持ち、文言は Runtime
  （`handler.ts`）とフロントエンド（`error-guidance.ts`）それぞれが同じ固定文言を持つ
  （ADR-0002: 表示メタデータは UI 側の関心事だが、Runtime 側もログではなく応答本文として
  同じ文言を返す必要があるため、両方に定数として存在する）
