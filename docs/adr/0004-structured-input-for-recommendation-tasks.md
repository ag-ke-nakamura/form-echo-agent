# 推薦系タスクは Runtime へ構造化入力を渡す

- **Status**: accepted（ADR-0005 が `input` を全 taskId へ広げたため、「推薦系だけ」という限定はもう効かない。`INPUT_SCHEMAS` の形と、構造化入力に自由文字列を置かないという制約はそのまま生きる）
- **Date**: 2026-09-03

ADR-003 は Runtime へのリクエストを `{taskId, prompt, sessionId}` の3つに閉じ、画面が持っている状態を渡さないと決めた。**これは入力が自然文であるタスク（抽出系）についての決定である。** 推薦系 `meeting.recommend-schedule`（#981 候補日提案）は入力が参加可否表という構造化データで、自然文だけでは原理的に成立しない — 誰がどの候補日程に○を付けたかを見ずに順位は付けられない。

そこでリクエスト契約に `input` を足し、`taskId` ごとの入力スキーマを `INPUT_SCHEMAS` として `OUTPUT_SCHEMAS` と対称に持つ。**ADR-003 は抽出系3タスク（`ic-card.parse-reservation`、`meeting.parse-candidates`、`meeting.parse-availability`）に対して有効なまま**で、それらの `INPUT_SCHEMAS` は `null`（自然文だけ）を明示する。

**ADR-003 が書いた見直し条件は的を外していた。** あちらは「IDでしか表せない要求（特定の候補日程への言及を AI に解決させる等）が出た時点で見直す」としたが、実際に見直しを迫ったのは別の軸だった — **入力が自然文でないタスクが現れたこと**である。IDは今も不要で、候補日程は `{日付, 開始時刻, 終了時刻}` の3項目の組で一意に指せる。画面だけの行識別子を契約に持ち込まない線は動いていない。

## Considered Options

- **任意フィールド `context` を足す**: ADR-003 が「リクエスト契約が `taskId` ごとに分岐し、3者が同一のリクエスト型を見るという `contracts/` の前提が弱くなる」として却下した案。しかしこの反論は成立しない — `OUTPUT_SCHEMAS` は既に `taskId` ごとに分岐しており、3者が同一に見ているのは**表**であって個々のスキーマではない
- **`taskId` で discriminated union にする**: 既存3タスクのリクエスト型まで書き換わる
- **フロントエンドまたは BFF が参加可否表を `prompt` に文字列で埋め込む**: ADR-003 の却下理由（`prompt` が「ユーザーが書いた文」と「システムが組み立てた文」の混合物になり、入力サニタイズと Guardrail チェックが何を検査しているのか曖昧になる）がそのまま生きている
- **`INPUT_SCHEMAS` を `OUTPUT_SCHEMAS` と対称に置く（採用）**: base は `{taskId, prompt?, sessionId, input?}` のまま。`null` を明示的に置くのは `domain-agent.ts` の `tools: []` と同じ理由で、「まだ足していない」と「足さないと決めた」を区別するため

## Consequences

- **`prompt` が任意になる。** 推薦系は参加可否表だけで成立し、「AI提案」ボタンを押すだけで送れる必要がある。固定文を画面が埋めるのは上で却下した案そのものなので採れない。`prompt` と `input` のどちらが必須かは `taskId` ごとに表で持ち、どちらも欠けた状態は表が弾く
- **`input` は Guardrail チェックとサニタイズの対象にしない。** これらが検査しているのは利用者が書いた文であり、システムが組み立てた構造化データを同じ検査に通すと「何を検査しているのか曖昧になる」が経路を変えて戻る。代償として **`input` に自由文字列を置かない** — 参加者は `/^参加者[A-Z]$/` に縛り、表示名は画面が作る。ここを自由文字列にすると prompt injection の窓になる
- **BFF が入力と出力の両方を見るので、提案が入力の候補日程と一致しているかを検査できる。** 抽出系には無かった検査で、AI が入力に無い候補日程を返した場合を BFF の段で捉えられる。ADR-003 が「フロントエンドで黙って落ちる」と書いた失敗の、推薦系における手当てになる
- **`input` は追加指示のときも毎回再送する。** `domain-agent.ts` の Agent キャッシュは「ベストエフォート。コールドスタートで消える」と明記されており、会話履歴が消えることは想定済みの正常な状態である。初回だけ送ると、履歴が消えた後の追加指示が「表の無いリクエスト」として届き、AI は順位を付ける対象を持たないまま実行させられる。`sessionId` はフロントエンドが持ち続けるので、この経路はセッションを作り直しても塞がらない
- 同じ会話に参加可否表が複数回現れるため、`SKILL.md` に「複数回与えられた場合は最後のものだけを使う」と書く必要がある。JSON Schema に写らない制約なので、`outputs.ts` の `start_time < end_time` と同じくプロンプト側で言うしかない
- ADR-003 の突き合わせ（フロントエンドが日付で当てる）は推薦系では3項目の組になる。`candidates-panel.tsx` の `candidateDates()` は日付を `Set` で畳むので、推薦系の入力には使えない。同じ候補日程の列から2通りの見え方を作ることになる
