# 交通ICの入力をフォーム主導にする

- **Status**: accepted
- **Date**: 2026-09-09
- **Amends**: [ADR-0004](0004-structured-input-for-recommendation-tasks.md)（`input` に自由文字列を置かないという縛り）・[ADR-0005](0005-runtime-receives-screen-state.md)（`ic-card.parse-reservation` の `input` が `null` であること、および「4つの画面デザイン設計を画面の正典とする」という数え方）

クライアントから交通ICの運賃AI検索について2つの文書が来た（`temp/design/fare-search-ai-screen-design.md` は画面設計指南書、`temp/ic-card-prompt-sample.md` はプロンプトサンプル）。どちらも**職員がフォームを埋めてから AI を呼び、AI はフォームを読んで経路と運賃を計算する**流れを前提にしている。サンプルは `"出発地"` `"目的地"` `"片道／往復"` `"追加指示"` をすべて入力項目名として参照し、指南書は追加指示を「※任意」としている。

我々の実装は逆向きだった — 自然文から出発地・目的地を抽出してフォームに入れる。この向きだと、**職員が出発地・目的地を選んで追加指示に何も書かずに生成を押したとき、AI には材料が何も無く経路が空で返る。** 指南書の主な流れが成立しない。

そこで **`ic-card.parse-reservation` の `input` に 出発地・目的地・往復区分を載せる**（ADR-0005 の表から `null` が消える）。あわせて `PROMPT_REQUIREMENT` を `'optional'` にする — 与件だけで AI にできることがある状態になったので、`meeting.recommend-schedule` と同じ形になった。

## Guardrail チェックの境界を引き直す

ADR-0004 は `input` を Guardrail チェックの対象にせず、代償として「`input` に自由文字列を置かない」と縛った。出発地・目的地は建物名・会社名を許す自由文字列なので、この縛りに正面から当たる。

**縛りを外すのではなく、ADR-0004 の原則をそのまま適用する。** あの ADR が書いているのは「検査しているのは**利用者が書いた文**であり、システムが組み立てた構造化データを同じ検査に通すと『何を検査しているのか曖昧になる』が経路を変えて戻る」である。出発地・目的地は職員がフォームに打った（または選択肢から選んだ）**まさに利用者が書いた文**なので、検査に通すのが原則どおりの扱いになる。

したがって境界は「`prompt` か `input` か」ではなく「**人が書いた文字列か、システムが組み立てた与件か**」になる。会議3タブの `input`（参加者の識別子・候補日程の識別子・所要時間・参加可否）はシステムが組み立てた与件のままで、検査対象に入らない。**`input` に自由文字列を置かないという縛りは、この1辺を除いて生きている。**

検査は `prompt`・出発地・目的地を**1本のテキストに連結して1回**行う（`invoke-task.ts`）。呼ぶ回数が増えないだけでなく、**欄を跨いだ注入**（出発地に前半・追加指示に後半を書く）が捕まる — 欄ごとに検査すると素通りする。ブロック時の文言は欄名を含まないので（ADR-0009）、どの欄が原因かを分ける必要は無い。

`sensitiveInformation` の検知対象から `ADDRESS` / `NAME` を外してあることがここで効く（`docs/reference-doc-fixes.md` F-06）。外していなければ、出発地「虎ノ門ヒルズ」が confidence 1.0 で検知されて主な流れが毎回ブロックされる。

## 画面の正典を数え直す

ADR-0005 は「`temp/design/` の**4つ**の画面デザイン設計を画面の正典とする」と書いた。指南書は5本目で、出自も違う（クライアントPDFの書き起こし。他4本は我々の設計）。**指南書の指摘を `reservation-ai-screen-design.md` へ吸収し、正典は4本のままとする。** 2本並べると、交通ICタブの仕様を読むのに突き合わせが必要になり、食い違ったときにどちらが正か画面から読めない。

プロンプトサンプルは `temp/` に残す。Skill の本文（`skills/ic-card/parse-reservation.ts`）が実際にモデルへ渡る唯一のもので、そこが正典である。同じディレクトリに2本の指示文書を並べると、どちらがモデルに渡るのか構造から読めなくなる。残すのは、サンプルとの差分がなぜ生まれたのか（同行者の氏名を受けない・バスの扱い・往復割引を捨てた等）を後から確かめる手がかりのため。

## Considered Options

- **抽出モデルを維持し、往復区分だけ与件にする**: 契約の変更が最も小さいが、上記のとおり指南書とサンプルの流れが成立しない（追加指示が空だと材料が無い）
- **出発地・目的地を与件と抽出の両方から受け、どちらが勝つかを決めない**: 職員が結果を予測できない画面になる。**規則を明示すれば採れる**ことが分かったので、これは ADR-0018 で解いた
- **フォーム主導にし、Guardrail の境界を引き直す（採用）**

## Consequences

- **`input` を持つ taskId が4つになり、`INPUT_SCHEMAS` に `null` が1つも無くなる。** ADR-0004 が `null` を明示した理由（「まだ足していない」と「足さないと決めた」の区別）は、これで交通ICについては役目を終える
- **`buildUserMessage` の交通IC分岐が消える。** `HEADINGS` の型が `INPUT_SCHEMAS[K] extends null` に連動しているので、見出しを埋めることが型から要求される（`input: 'フォームの入力内容'` / `prompt: '職員からの追加指示'`）
- **追加指示が空の回でも入力側の Guardrail チェックが走る。** 現在の検査は `if (prompt !== undefined && prompt !== null)` で守られているので、`'optional'` にするだけだと**主な流れで検査が1度も走らない**。`input` の自由文字列を検査対象に入れるのは「あったほうがよい」ではなく、この穴を塞ぐために必要である
- **`input` は追加指示のときも毎回再送される**（ADR-0004）ので、同じ会話にフォームの内容が複数回現れる。Skill に「複数回与えられた場合は最後のものだけを使う」が要る — 会議の参加可否表と同じ手当て
- 出発地・目的地は正規表現で縛れない。`input` の値に形の制約を掛けるという ADR-0004 の手筋（参加者は `/^参加者[A-Z]$/`）が、この2欄には使えない。だから検査で受ける
- `.claude/rules/contracts.md` の「`input` はサニタイズも Guardrail チェックも通さないので自由文字列を置かない」と `input` の表は、この ADR に合わせて直す必要がある
