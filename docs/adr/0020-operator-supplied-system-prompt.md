# 職員が system prompt を持ち込む taskId を置く

- **Status**: accepted

## 決定

5つめのタブ（プロンプト検証）に対応する taskId `playground.free-prompt` を置く。この taskId
に限り、

- **system prompt は職員が書いた文（持ち込みシステムプロンプト）そのもの**である。
  `SKILLS[taskId]` は持たず、我々が足すのは基準時刻の付記1つだけ
- **出力は Structured Output を通らない。** 出力契約は `{ text }`（回答本文）だけを持ち、
  `invokeWithSchemaRetry` を経由しない2本目の経路で返す
- **応答封筒に実効システムプロンプトを載せて画面へ返す**（この taskId のときだけ値が入る）
- **会話履歴は、持ち込みシステムプロンプトが前回と同じときだけ継続する。** 変われば
  `discardSession` して作り直す
- **非AI経路を持たない**（`CONTEXT.md` の当該語をこの ADR に合わせて狭めた）

Web 検索は持つ（`DOMAIN_TOOLS` に検証ドメインの行を足す。上限は交通ICと同じ3回）。
Guardrail チェックは他タブと同様に入力側・出力側とも効かせ、入力側の検査対象には
持ち込みシステムプロンプトと検証メッセージの両方を含める。

## なぜ

この画面の目的は**プロンプトそのものの効きを測る**ことで、他4タブのように UI と AI 出力が
噛み合っていることではない。その目的に対して、我々が黙って足すものはすべてノイズになる。

- **Skill を足さない**のは、足した瞬間に職員が見ているのが「自分が書いた文の効き」ではなく
  「自分が書いた文 + 我々の文」の効きになるため。検証画面としてはそこで壊れる
- **Structured Output を通さない**のは、あれがスキーマをツール仕様に変換してモデルに
  ツール呼び出しを強制する仕組みで、**素の system prompt の効きを見るという目的そのものを
  歪める**ため。既存4タブが全部 Structured Output 経由である以上、素の挙動と比べる基準線が
  どこかに要り、それがこの画面になる
- **基準時刻だけは残す**のは、他タブとの比較で「基準時刻がある状態のモデル」を揃えるため。
  ただし足したことを隠さない — 実効システムプロンプトを画面へ返すのはそのためで、
  渡したものが読めない検証画面は成立しない
- **履歴を持ち込みシステムプロンプトで区切る**のは、再現性のため。履歴が残ると「同じ入力で
  違う答え」が履歴のせいかモデルのゆらぎか切り分けられない。一方 system prompt が同じなら
  追い質問は自然な検証行為なので、そこまで捨てる必要は無い

## Considered Options

- **入力欄を1つにし、それを system prompt にする**: 「同じ user message に対して system
  prompt を差し替えて比べる」という検証の主な使い方ができない。2欄あれば user message を
  空にして1欄を再現できるが、逆はできない
- **`{ answer, sources }` 程度の最小スキーマで Structured Output を通す**: 上記の理由で
  却下。素の text を返す経路が1本増える代償は、目的に照らせば安い
- **持ち込みシステムプロンプトを `prompt` に、検証メッセージを `input` に載せる**:
  `prompt` の中身がモデルへ user message として渡らない唯一の taskId になり、契約の欄名と
  実体が食い違う。逆（`prompt` に検証メッセージ、`input` に持ち込みシステムプロンプト）を
  採った
- **キャッシュキーに持ち込みシステムプロンプトのハッシュを足す**: 編集して元に戻すと古い
  履歴が蘇る。既存 Agent の `systemPrompt` と比べて違えば捨てる形にした
  （`getOrCreateDomainAgent` は既にキャッシュヒット時に `systemPrompt` を貼り直しており、
  貼り直す前に比較を1つ挟むだけで済む）

## Consequences

- **`prompt` 欄が運ぶのは検証メッセージであって持ち込みシステムプロンプトではない。**
  用語が逆に読めるので、`CONTEXT.md` の両方の項がこれを明記している
- **サニタイズのタグ除去（`<[^>]+>` の剥ぎ取り）をこの taskId では掛けない。** 掛けると
  検証メッセージからだけ `<thinking>` の類が消え、持ち込みシステムプロンプト（`input`
  経由なのでサニタイズを通らない）からは消えないという非対称になる。**画面が回答本文を
  確実にエスケープして描くことがこの決定の前提条件**である
- 持ち込みシステムプロンプトにも `MAX_PROMPT_LENGTH`（10,000字）を掛ける。`input` 側の
  スキーマで持つ。既存の Skill 全文を貼っても収まる
- 失敗時の案内はこの taskId 専用の文言を持つ。他タブの「手動で入力してください」は非AI経路
  が無いこの画面では嘘になる。`PARSE_FAILED` はこの経路では起きえない
- 出典は回答本文の下に `citations` の一覧として出す。ADR-0019 の出典番号方式は
  **成立しない** — 番号で指せと指示する Skill がこの画面には無いため。番号方式を試したい
  職員は自分の持ち込みシステムプロンプトにそう書けばよく、それが効くかを試せること自体が
  この画面の値打ちになる
- ストリーミングはしない。Runtime・BFF・画面の3層に新しい経路が要る割に、この画面が答え
  たい問いには寄与しない
