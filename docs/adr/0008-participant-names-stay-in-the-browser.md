# 参加者の実名を Runtime へ送らず、画面で解決する

- **Status**: accepted
- **Date**: 2026-09-04

候補日提案の入力に参加者の**識別子だけ**を載せ、実名を Runtime へ送らない。AI が返す欠席者・未回答者も識別子で返す。画面に「欠席: 山田太郎、佐藤花子」と実名で出すのは、フロントエンドが手元の名簿で識別子を解決した結果とする。

ADR-0004 は構造化入力（`input`）がサニタイズも Guardrail チェックも通らないことを理由に、参加者を `参加者A` の形に縛った。検査を通さない値に自由文字列を許すと、そこが prompt injection の窓になる。一方で設計書は統制要件の「説明責任」として、提案の根拠に欠席者の実名を出すことを求めている（`metrics.absent_names: ["山田太郎", "佐藤花子"]`）。

この2つは両立する。設計書が実名を出したいのは**表示**であって、AI に名前を推論させたいわけではない — `absent_names` は参加可否表の集計結果にすぎない。名前を送らなければ ADR-0004 の根拠は保たれたまま、画面には実名が出る。

## Considered Options

- **`参加者A` を画面表示にも使う**: ADR-0004 は無傷だが、設計書の「説明責任」要件を満たせず、ADR-0004 の制約を回避する経路を作った意味も無くなる
- **実名を許し、構造化入力にサニタイズと Guardrail チェックを通す経路を新設する**: 設計書に最も忠実。ただしこの検証環境が検証したいこと（Guardrail の精度）とは別の複雑さを1層持ち込む
- **識別子で送り、画面で解決（採用）**

## Consequences

- `input` に自由文字列を置かないという ADR-0004 の制約が、ADR-0005 で広がった `input` 全体に適用できる形で残る。交通ICの目的（`purpose`）を自由文字列にせず選択肢にしたのも同じ理屈
- AI が書く `comment` は「参加者2名が参加できないため」のように**人数**で語るか、識別子で語るかのどちらかになる。識別子で語らせる場合、画面がその文中の識別子も実名に置き換える必要がある
- 本番で参加者が個人情報を持つレコードになったとき、この境界がそのまま「AI へ渡さない範囲」の線になる
