# 手入力かどうかを Runtime に渡す

- **Status**: accepted
- **Date**: 2026-09-09
- **Builds on**: [ADR-0017](0017-ic-card-input-driven-by-form.md)（交通ICの `input` に出発地・目的地・往復区分を載せた）

ADR-0017 で運賃の額を決める与件（出発地・目的地・往復区分）を `input` に載せた。これらは出力契約にも載っている — 追加指示で別の場所が明示されたときは AI が直せる必要があるためで、規則はプロンプトサンプルの禁止事項が既に書いている（「ユーザーが言及していない事項を勝手に編集すること」）。

**ところがサンプルはもう1つ禁止事項を持っていて、この2つが衝突する。**

- 「ユーザーが**手動で入力済み**の項目をAIが変更・上書きすること」→ 出発地に触るな
- 「ユーザーが"追加指示"で…指定した場合は、これを踏まえて経路を選定する」→ 追加指示の場所で経路を引け

**手入力の出発地と追加指示が食い違ったときどちらに従うのか、サンプルにも指南書にも書かれていない。** 従わせ方を決めないと、次のフォームができる。

職員が手で「霞ヶ関」と打ち、追加指示に「新宿から」と書いた場合。AI が追加指示に従うと `origin: "新宿"` と新宿からの経路・運賃・最寄を返す。反映すると **`isPreserved`（手入力は上書きしない。#38）が出発地だけを守るので、出発地は霞ヶ関のまま残り、移動経路と運賃は新宿から計算されたものが入る。** 出発地と移動経路が違う場所を指すフォームができ、なぜ経路が新宿から始まっているのかは画面のどこにも出ない。

そこで **`input` に値だけでなく「職員が手で入れたか」を載せる。**

```
input = {
  origin:      { value: "霞ヶ関駅（東京都）", is_manual: false },
  destination: { value: "虎ノ門ヒルズ",       is_manual: true  },
  round_trip:  { value: "round",              is_manual: false },
}
```

規則は `is_manual` で割る。

- **`is_manual: false`（既定値のまま、または前回 AI が入れた値）** — AI が勝つ。追加指示の場所で経路を引き、その欄も書き換える。禁止事項の「手動で入力済み」に当たらない
- **`is_manual: true`（職員が手で入れた）で追加指示と食い違う** — 矛盾として聞き返す。`route_candidates` を空で返し、`message` で「出発地は霞ヶ関ですか、新宿ですか」と尋ねる。フォームは変わらない

食い違っているかの判定は AI 側に置く。画面で文字列比較すると「新宿」と「新宿駅」が食い違いになる。

これは #69（カレンダーの表示範囲を渡す）と同じ形である — **画面が持つ制約は画面が渡す。** 手入力かどうかを知っているのは画面だけで、Runtime からは値しか見えない。

## `is_manual` の出どころ

画面の `FieldSource` から導く（`is_manual = source === "manual"`）。この判断のために `FieldSource` に3つ目の状態 `"default"` を足す — いまは `"manual" | "ai"` の2値で、**プレプリント値が `"manual"` に落ちてしまう**（`EMPTY_FORM` が全欄 `source: "manual"` なので、指南書が求める「出発地に霞ヶ関、目的に打ち合わせをプレプリント」を入れると `isPreserved` が true を返し、職員が手を触れていない欄が守られる）。

`"default"` を初期状態にすると副産物が1つ付く。「空で `manual`」が**職員が意図して消した欄**だけを指すようになるので、`isPreserved` を `source === "manual"` だけに縮められ、**消した AI 由来の欄が次の反映で埋め直される**という既知の穴（`reservation-form.ts` の `applyToForm` の但し書き）が閉じる。あのコメントが「分けるには `FieldSource` に3つ目の状態が必要」と書いていたのはこの穴のことで、同じ1つの状態で両方が解ける。

`source: "ai"` が `is_manual: false` になるのは正しい。AI バッジは「再生成で上書きされる範囲」の印でもある（#38）ので、AI が入れた値を AI が直せる状態と一致する。

## Considered Options

- **常に手入力のフォームが勝つ**（AI は追加指示の場所を無視し、`message` で無視したと言う）: 職員が書いた「新宿から」が黙って捨てられる
- **常に AI が勝つ**（出発地・目的地・往復区分だけ手入力の保護を外す）: サンプルの禁止事項を正面から破る
- **常に聞き返す**（既定値のままでも尋ねる）: プレプリントを放置したまま追加指示に場所を書くのは普通の使い方で、そこで尋ねると往復が毎回増える。サンプルの禁止事項「解釈ルールで対応できる曖昧表現に対して不必要な確認質問をすること」に当たる
- **`is_manual` で割る（採用）**: サンプルの2つの規則を両方守りながら、自己矛盾したフォームを作らない唯一の枝

## Consequences

- **規則が掛かるのは運賃の額を決める3つの与件だけ**（出発地・目的地・往復区分）。利用目的と出発日時は経路計算に使わないので、手入力が守られて AI の抽出が入らなくても**フォームは自己矛盾しない** — 既存の `ApplyReport` の「守った: 利用目的」で足りる
- **`FieldSource` は4タブが使う**（`ic-card` / `candidates` / `availability` / `recommend` の6箇所）。会議3タブは `"default"` を生成しないので挙動は変わらないが、`source === "manual"` を「AI 由来でない」の意味で読んでいる箇所は全部見直す必要がある
- 聞き返しの回は `route_candidates` が空になるので、移動経路と1人あたり運賃が `null` の行として残りプレビューが黄になる。反映ボタンは出ない（押しても変わらないので正しい）
- `is_manual` の**規則そのもの**は Skill（`skills/ic-card/parse-reservation.ts`）が持つ。`buildUserMessage` で整形して印を付ける案は採らない — 振る舞いの規則が2ファイルに散り、Skill だけ読んで挙動が追えなくなる。`input` は JSON のまま渡す
