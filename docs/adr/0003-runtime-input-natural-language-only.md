# Runtime へ渡す入力を自然文だけに閉じる

- **Status**: accepted（推薦系タスクについては ADR-0004 が限定する）
- **Date**: 2026-09-03

BFF から Runtime へ渡すリクエストは `{taskId, prompt, sessionId}` の3つだけとし、**画面が既に持っているフォームの状態（候補日程の一覧、入力済みの値、レコードのID）を Runtime へ渡さない**。ドメインエージェントは自然文だけを見て構造化データを返し、それを画面の状態と突き合わせるのはフロントエンドの仕事とする。

きっかけは `meeting.parse-availability`（参加可否回答）。「15日と17日は大丈夫ですが16日は無理です」を参加可否に落とすには「何に対する可否か」が要る。候補日程の一覧をリクエストで運べば AI が候補日程を特定できるが、採らなかった。ユーザーの自然文が言っているのは**日付**であって候補日程IDではないので、IDへの解決は AI にとって余計な仕事であり、外したときに何が起きたか説明しにくい。出力は `{date, available}` の写像に留め、自分の候補日程の一覧との突き合わせはフロントエンドが素直な代入で行う。

## Considered Options

- **リクエスト契約に `context` を足し、`taskId` ごとに形を決める**: 本番では候補日程が DB のレコードになりIDを持つので、その形に最も近い。ただしリクエスト契約が `taskId` ごとに分岐し、「3者が同一のリクエスト型を見る」という `contracts/` の前提が弱くなる
- **フロントエンドまたは BFF が候補日程の一覧を `prompt` に文字列で埋め込む**: 契約は増えない。ただし `prompt` が「ユーザーが書いた文」と「システムが組み立てた文」の混合物になり、入力サニタイズ（最大10,000文字・タグ除去）と Guardrail チェックが何を検査しているのかが曖昧になる
- **自然文だけに閉じる（採用）**

## Consequences

- 突き合わせのロジックがフロントエンドに置かれる。#23 の Testing Decisions は「出力契約からフォーム状態への写像は素直な代入に留め、条件分岐が育った時点で見直す」としており、この突き合わせがその線引きを試す最初の例になる
- AI が入力に無い日付を返した場合、フロントエンドの候補日程の一覧に一致するものが無く黙って落ちる。`message` が何を読み取ったかを説明することが、この経路の唯一の手当てになる
- 突き合わせの対象となる候補日程の一覧を、画面側が**答える前に持っている**必要がある。参加可否タブは候補日程を作らない（AI も職員も、作るのは候補日程タブ側）ため、この一覧をどちらのタブの内側にも置けず、状態の持ち主はタブ層になる。ADR-002 の「3者が同一の契約を見る」は変わらず、Runtime へ渡すものも増えていない
- 本番で候補日程がレコードIDを持つようになっても、この決定を引き継ぐ限り Runtime はIDを知らないままになる。IDでしか表せない要求（特定の候補日程への言及を AI に解決させる等）が出た時点でこの ADR を見直す
