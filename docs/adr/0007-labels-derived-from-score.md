# AI評価ラベルは評点から契約側の関数で導く

- **Status**: accepted
- **Date**: 2026-09-04

候補日提案で AI が返すのは**評点（`score`）と根拠（`comment`）だけ**とし、AI評価ラベル（推奨／予備に提案／要検討／条件合わず／参加入力未済）・開催日の初期選択・予備日の初期選択は、すべて `contracts/` に置く関数が評点と集計値から導く。AI にラベルを返させない。

設計書 7.2節はラベルを評点の範囲で決める表を持ちながら、同じレスポンスに `recommended_candidate_id` と `backup_candidate_ids` も別フィールドとして持っている。同じ判断が評点・ラベル・専用フィールドの3箇所に現れており、AI に3通りの言い方で同じことを返させると矛盾した組が出る。CLAUDE.md の「同じ判断を2箇所に書かない」を、`checkTaskInput` / `outputSchemaFor` と同じ形で守る — BFF の再検査もフロントエンドの表示も同じ関数を引く。

**「参加入力未済」だけは評点から導かない。** 設計書は 7.2節で参加可能率29%以下、10.3節で回答率30%未満と、同じラベルに2つの基準を与えていて矛盾している。全員が「欠席」と答えた候補日程（回答率100%・参加可能率0%）がどちらになるか決まらない。語義どおり**回答率**で判定し、7.2節の表からは外す。

## Considered Options

- **設計書どおり AI が `label` も `recommended_candidate_id` も返し、整合性を `refine` で検査する**: 設計書の字面に最も忠実。ただしラベルの境界値付近で矛盾が出るたびに Structured Output の再試行が走る
- **AI が `label` を返し `score` を持たない**: 同点の候補日程を区別できず、ラベル内の並び順が決まらない
- **評点から導く（採用）**

## Consequences

- 閾値を動かしてもモデルへの指示を書き換えずに済む。プロンプト検証がこの検証環境の目的である以上、閾値の調整とプロンプトの調整を分離できることに意味がある
- AI は「どの候補日程が推奨か」を直接は言わない。`comment` は自分に付いた評点の理由を書くだけで、全体の中の位置には触れない。従来の契約が持っていた「順位は 1..N の順列」という欄をまたぐ不変条件は不要になる
- 集計値（参加可能人数・現地／リモートの内訳・欠席者・未回答者数）は AI ではなく画面と契約側の関数が参加可否表から数える。AI が数を間違える余地が消える
