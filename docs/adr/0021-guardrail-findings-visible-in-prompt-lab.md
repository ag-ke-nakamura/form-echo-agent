# プロンプト検証タブに限り Guardrail の findings を画面に出す

- **Status**: accepted
- ADR-0009 を `playground.free-prompt` の1点に限って改訂する

## 決定

`playground.free-prompt`（ADR-0020）でブロックが起きたときに限り、**反応したチェック種別と
スコア**（`severityScore` / `confidenceScore`、検知した PII 型）を画面へ出す。他4タブは
ADR-0009 の固定文言のままで、変更しない。

出力側でブロックされた場合、**回答本文は見せない。** ブロックされた事実と findings だけを
返す。

## なぜ

ADR-0009 が原因を隠す理由は「文言の違いが検知を回避する言い回しを探すオラクルになる」こと
と「職員の取る行動が変わらない」ことだった。**プロンプト検証タブでは後者が成り立たない** —
この画面の職員の仕事はまさにプロンプトを直すことで、種別だけでは二値しか分からず、直した
効果を測れない。「Guardrail が何をどれだけ強く止めるか」を観測すること自体がこの検証環境の
目的に含まれる。

前者（オラクルになる）は残る。**それを承知の上で受け入れる** — この画面は職員向けの業務機能
ではなく検証の道具であり、同じ職員が実測のためにログを読める立場にいる。画面へ出すのは、
ログを読みに行く往復を省くだけで、渡している情報は増えていない。

出力側で回答本文を見せないのは、見せると出力側チェックを置いた理由（F-16。Structured
Output のツール引数を Guardrail が評価しないため、抽出結果に載った PII をアプリケーション層
で捕まえる）を自分で潰すため。ブロックされた本文が見たいなら Guardrail を切った環境で見る
べきで、この画面の役目ではない。

## Consequences

- `handler.ts` が `GuardrailBlockedError` の `verdict` を握りつぶすのは他4タブに対してだけ
  になる。taskId で分岐が1つ増える
- ADR-0009 の「`GuardrailFinding.detail` はログにしか出さない」は、この1点で成り立たなく
  なる。あちらを読む人がここへ辿れるよう、ADR-0009 側にも参照を足す
