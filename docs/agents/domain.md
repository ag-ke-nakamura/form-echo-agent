# Domain Docs

エンジニアリング系スキルがコードベースを探索するとき、このリポジトリのドメインドキュメントをどう読むか。

## 探索の前に読むもの

- リポジトリルートの **`CONTEXT.md`**
- **`docs/adr/`**: これから触る領域に関わる ADR を読む。

これらのファイルが存在しない場合は**黙って先に進む**。不在を指摘したり、先回りして作成を提案したりしない。`/domain-modeling` スキル（`/grill-with-docs` と `/improve-codebase-architecture` から到達する）が、用語や決定が実際に固まった時点で遅延生成する。

## ファイル構成

このリポジトリは **single-context** レイアウトを採る。

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
├── agent-app/
├── hono-app/
└── nextjs-app/
```

`agent-app` / `hono-app` / `nextjs-app` は独立したプロジェクトだが、ドメイン用語と決定は単一の `CONTEXT.md` と `docs/adr/` に集約する。プロジェクトごとにドメインが完全に分岐して単一の用語集が破綻したら、ルートに `CONTEXT-MAP.md` を置いてプロジェクト単位の `CONTEXT.md` を指す multi-context 構成へ移行する。

## 用語集の語彙を使う

出力がドメイン概念を指すとき（issue のタイトル、リファクタ提案、仮説、テスト名）は、`CONTEXT.md` で定義された用語を使う。用語集が明示的に避けている同義語に流れない。

必要な概念が用語集にまだ無いなら、それはシグナルである。プロジェクトが使っていない言葉を発明しているか（考え直す）、本当のギャップがあるか（`/domain-modeling` 向けに記録する）のどちらか。

## ADR との矛盾を明示する

出力が既存の ADR と矛盾するなら、黙って上書きせず明示的に表面化させる。
